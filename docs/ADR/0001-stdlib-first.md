# ADR-0001：后端只依赖标准库 + 三个小库

- 状态：已采纳
- 日期：2026-09-20
- 相关：`docs/REQUIREMENTS.md` §1 技术栈

## 背景

LMBY 的立项理由就是「Emby/Jellyfin 太重」。如果实现阶段一路引入 ORM、代码生成器、
迁移工具、依赖注入框架、Web 框架……最终会复刻出同样的复杂度。因此需要一条明确的技术纪律：
**每一层都先问「标准库能不能做」。**

同时要考虑部署现实：用户要自己拉容器跑起来，构建链路越短越好，
最好「一条 `docker compose up` 就能用」。

## 决策

### 1. 路由用标准库 `net/http`，不引入 chi/echo

Go 1.22 起 `ServeMux` 原生支持方法 + 路径参数（`GET /api/v1/items/{id}`），
配合 `r.PathValue("id")` 已经覆盖本项目所有需求。
中间件就是普通的 `func(http.Handler) http.Handler`，自己写 20 行足够。

**放弃 chi 的原因**：它能提供的额外价值只有路由分组与少量工具函数，
不足以换取一个外部依赖。

### 2. 数据访问用 pgx + 手写 SQL，不引入 sqlc/ORM

- `pgx/v5` 直接对接 PostgreSQL，扫描到结构体，SQL 完全可见。
- 不用 sqlc：它需要在每台开发机和 CI 上装一个代码生成二进制并维护 `sqlc.yaml`，
  对一个查询语句并不复杂的项目来说是负收益。
- 不用 GORM 之类：隐式行为多，复杂查询最后还是得写原生 SQL，等于多学一套。

**代价**：手写扫描代码有样板量。可接受，因为可以封装 `scanUser(row pgx.Row)` 这类小函数收敛。

### 3. 迁移用自研的内嵌迁移器，不引入 golang-migrate/goose

`migrations/*.sql` 通过 `go:embed` 打进二进制，运行时：
- 用 `pg_advisory_lock` 保证多实例并发安全；
- 每个文件在自己的事务里执行；
- 记录每个迁移的 sha256，历史迁移被改动时直接报错（防止有人在生产上偷改老迁移）；
- 迁移脚本是多条语句，必须走 `PgConn().Exec()`（简单查询协议），
  否则 pgx 的扩展协议会拒绝「一次多条命令」。

**收益**：零外部二进制、零版本管理麻烦，`lmby serve` 启动即自愈。

### 4. 任务队列用 PG 表，不引入 Redis/MQ

`tasks` 表 + `for update skip locked` + 进程内 worker 池。
进程重启后未完成的任务自然还能被捡起来，不需要额外的持久化设计。

### 5. Node 只在构建期，运行期零 Node

前端 React + TypeScript + Vite，产物 `go:embed` 进 Go 二进制。
部署物因此只有两件：**一个二进制 + 一个 PostgreSQL**。

### 6. 前端样式先用原生 CSS 变量，暂不引入 Tailwind

明暗主题本来就依赖 CSS 自定义属性；在 UI 复杂度真正上来之前，
引入 Tailwind 只是多一层构建配置和一个版本升级负担。
M6 若发现手写 CSS 成为瓶颈，再引入并在此追加一条 ADR。

## 后果

**正面**
- 依赖树极小：`pgx`、`x/crypto`、`BurntSushi/toml` 三个直接依赖。
- 构建链路短：`go build` 即可，没有代码生成步骤。
- 部署简单：单二进制 + 一个数据库容器。

**负面**
- 手写 SQL 与扫描样板代码需要自律，否则容易散乱。
  → 约束：所有查询都放在 `internal/store/*.go`，每个实体一个文件。
- 自研迁移器要自己保证正确性。
  → 约束：必须有针对迁移器的单元/集成测试（见 M1 任务列表）。
- 前端到 M6 可能需要回头补构建工具链。
  → 已知并接受。

## 与需求文档的差异

`docs/REQUIREMENTS.md` §1 原文写的是「`chi` 或标准库」与「`pgx` + `sqlc`」，
本 ADR 将其收敛为纯标准库 + 手写 SQL，文档已同步更新。
