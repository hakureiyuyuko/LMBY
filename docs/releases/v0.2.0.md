# LMBY v0.2.0 —— M4：转码与字幕

LMBY 是**纯 Web 在线播放**的轻量自托管媒体服务器：浏览器是唯一客户端，HTTP 是唯一出口，
一个 Go 二进制（前端 `go:embed` 进去）+ PostgreSQL，**运行期零 Node**，AGPL-3.0。

> 这是**第一个打 tag 的版本**。v0.1（M3「能看片」的状态）当时没有单独打过 tag，
> 所以下面的改动是从仓库起点一路到现在的汇总。

## 这一版的重点：转码

- **硬件能力真跑探测**：启动时实测 `-hwaccels` / `-encoders` / `-filters`，并**拿 1 秒小样真编一遍**，
  结果落盘缓存 —— 只有真跑通过的编码器才会被用。VAAPI 实测 11.8x；QSV / NVENC / VideoToolbox / AMF
  的参数照 Jellyfin 写、**未真机验证**（所以只在探测真跑通过时才会选它们）。
- **滤镜链**：HDR→SDR 走软件 `zscale`+`tonemap`（iHD 上 `tonemap_vaapi` 实测起不来）、10bit→8bit、
  去隔行、按分片长度强制关键帧对齐。
- **播放器画质档**：自动 / 原生 / 1080p…144p（只列比源低的档）。选了比源低的档，**即使本来能直出也转码**；
  切档从当前位置续播。
- **节流与回收**：预生成跑到客户端前面超过阈值就 `SIGSTOP` 暂停 ffmpeg（追上来 `SIGCONT`）；
  空闲回收进程与分片。
- **会话监控页**（管理员）：活跃会话、实时 fps / 速度 / 码率、一键终止。
- **错误不误伤**：硬解起不来（实测本机 iHD 解不了 H.264 High 10）会**自动降级成软件解码 + 同一个
  硬件编码器**；机器真编不了就如实给出理由，不把能看的片子变成「放不了」。

## 字幕：按「能不能还原原意」分三条路

- **ASS/SSA**：原样抽出交给前端 **libass**（定位、动画、卡拉OK、矢量绘图全保住），
  字体 = 服务端兜底字体（Noto Sans CJK，SIL OFL 1.1）**+ 容器内封的字体（mkv 附件）**。
- **纯文本（subrip 等）**：转 WebVTT 走浏览器原生轨道（后台单飞抽取 + 落盘缓存）。
- **图形字幕（PGS/VobSub）**：**烧进画面**（用户显式选择，界面会写明「需重新编码」这个代价）。

硬件加速的实测矩阵、踩到的坑与取舍（比如「为什么 HDR 不用 `tonemap_vaapi`」「为什么节流用
`SIGSTOP` 而不是往 stdin 写 p/u」）都写在 `docs/TRANSCODING.md`。文档里的数字都标注为
**实例测量值**，不是项目常量。

## 已知限制

- Windows / macOS 上不节流（无法暂停进程，优雅降级为「不节流」）。
- Safari / iOS 的原生 HLS 路径只是代码就位，**没有真机验证**。
- 外挂字幕的 GB18030 等编码探测、Trickplay（章节图/精灵图）、带宽自适应还没做。
- 图片写回媒体目录（像 nfo 那样）还没做，目前只读登记。
- 视频里**没有内封**的字体（字幕引用了但容器里没有）只能退化成兜底字体。

## 快速开始

见 [`docs/DEV-ENV.md`](https://github.com/hakureiyuyuko/LMBY/blob/main/docs/DEV-ENV.md)：
需要 PostgreSQL 与服务端 ffmpeg，配置放 `/etc/lmby/config.toml`，systemd 单元见 `deploy/`。

**Assets**：`lmby-linux-amd64` / `lmby-linux-arm64` / `lmby-linux-armv7` / `lmby-windows-amd64.exe`，
以及 `SHA256SUMS.txt`。
