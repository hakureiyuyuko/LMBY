# 直播电视（M5）设计笔记

> 这篇记的是**取舍与真跑实测**，不是教程。凡标「实测」的数字都是在一台真实实例上量出来的，
> 不是项目常量（换机器/换源都会变）。

## 一句话：直播不是「更长的点播」

点播那一套（`stream.Manager` + HLS）能复用，但直播必须在四处岔开：

| | 点播（转封装） | 直播 |
|---|---|---|
| 时间轴 | 有 `-ss` / `-t`，一段窗口 | 没有起点终点，连续流 |
| 播放列表 | `-hls_list_size 0`，留住全部分片（才能就地跳） | **滚动窗口**，只留最近 N 片，旧分片边滚边删 |
| 分片 | 4 秒 / fMP4 | **1 秒 / TS** |
| 节流 | 预生成超前就 `SIGSTOP` | **绝不节流**，源站本来就实时投递；暂停只会卡住画面 |

## 会话模型：一个频道一路 ffmpeg

- 会话 key 固定为 `live:ch<频道 id>`，所有观众共享它。两个人看同一频道 → 仍然只有一路 ffmpeg，
  也不会把源站拉两遍（IPTV 源站通常有并发限制）。
- 播放会话（浏览器标签页 / 外部播放器）只是「sid → 频道」的**内存映射**，不落库：
  进程重启后播放器反正要重新起播，落库只会留下永远清不完的僵尸会话。
- 停一路**不**踢人：只有该频道再没有别的观众时才真掐掉 ffmpeg。
- 「谁都不看了」由 `stream.Manager` 的空闲回收统一收口（配置项 `idle_seconds`）。

空回收的算术值得单独说：扫描是每 `reapInterval`（5 秒）一次，所以「空闲超过 N 秒」的会话
**最晚**要 N+5 秒才真的被杀掉。M5 的 DoD 是「无人观看后 45 秒内退出」，于是直播按
`IdleSeconds - reapInterval` 判定，实测落在 40~45 秒（点播仍按原阈值，避免动 M4 的行为）。

## 分片时长：为什么是 1 秒（实测逼出来的）

分片时长就是**起播延迟的下限** —— 播放器要先拿到一整片才能开播。同一个源上量：

| `-hls_time` | 第一个分片出来 |
|---|---|
| 2 秒 | 1859 ms |
| 1 秒 | **520 ms** |

DoD 要求浏览器起播 < 2 秒，2 秒分片会顶到上限（实测服务端到「首片可用」1351 ms）。
代价是请求数翻倍（本地网络无所谓）与客户端缓冲变短，所以滚动窗口放到 10 片（约 10 秒）。

其余 HLS 参数与原因：

- `-hls_flags delete_segments+omit_endlist+independent_segments+temp_file`
  - `delete_segments`：不删的话 24 小时能写掉几百 GB；
  - `omit_endlist`：播放列表滚动时不能补 `#EXT-X-ENDLIST`，否则播放器以为直播结束；
  - `temp_file`：分片先写临时文件再改名，避免把写了一半的文件发出去。
- `-hls_delete_threshold 3`：比列表多留 3 片，给正在拉旧分片的客户端一点容错。
- `-hls_segment_type mpegts`：直播固定 TS。fMP4 的 init 段在滚动窗口里要额外处理
  （客户端可能拿到已被删掉的 init），没必要。
- 播放列表与分片一律 `Cache-Control: no-store`：滚动列表被缓存住 = 客户端永远停在过去；
  而分片文件名会复用（`seg_00007.ts` 过一会儿是另一段内容），也不能缓存。

## 音视频参数

- 视频：`-c:v copy`，**直播不转码**（IPTV 源基本是 H.264 1080p，转码既没必要也吃 CPU）。
- 音频：`-c:a aac -b:a 192k -ac 2`。IPTV 源大多是 **MP2**，浏览器放不了，必须转。
- 映射用 `0:v:0?` / `0:a:0?`：直播源的流序号每次拉起来都可能不一样，而且有的源没有音轨；
  不带 `?` 的话 ffmpeg 会直接报错退出。
- 源站参数按协议给：rtsp 走 `-rtsp_transport tcp`（UDP 会偶发丢包花屏）+ `-timeout`（微秒）。

## 源站现实：一定有死源

真实订阅列表里死源不可避免。一次**全量真连探测**（S4 的 `probe`，每一台都连）实测量到：
**150 台里 67 台通、83 台不通** —— 不通的多数是「 8 秒内没有任何应答」（超时），
少数是源站直接回 5XX；而能用的那批 0.3~0.8 秒就返回流信息。

> 早先这里记的是「149 台里 26 台起不来」：那个数字来自播放验收脚本
> **「试到第一个能起播的就停」** 的路径（它只试了前 27 台），是下限不是总数。
> 同一时刻的串行探测与 4 路并发探测给出的判定**逐个一致**，所以那 83 台是源站真的不应答。

所以：

- 起播超时收到 **8 秒**。等越久用户越分不清是源坏还是自己网坏；8 秒对可用源绰绰有余。
- **失效源标记**（S4 已做，见下节）：`probe` / `probe_ok` / `probe_at` 由真连探测写入，
  界面上就能把通不了的频道理出来（M6 的界面标记）。
- 验收脚本会自动跳过死源（逐个试到能起播为止），不把「这台能不能用」写死成环境假设。

## 导入语义：地址是身份，用户态绝不覆盖

- **url 是频道的自然键**：同一个地址只更新元数据（名字、分组、logo、tvg-id、请求头、排序）。
- **停用状态、收藏、探测结果一律不覆盖**：否则每次刷新订阅源都会把用户手动停用的频道又打开。
  这也意味着「改分组」这类手工编辑会在下次导入时被播放列表里的值改回去 —— 这是有意的：
  播放列表才是频道的来源，用户态只包含「怎么用」，不包含「频道长什么样」。
- **删源不删频道**：用户可能只是不想再自动刷新了。
- **导入只清理本次来源自己的频道**：否则导入一个源会把另一个源的频道全删光。
- **空列表不清理**：订阅源偶发返回空内容（网络截断/CDN 出错）时，把用户频道全删是最坏的失败模式；
  这种情况直接报错。
- 接口不回显请求头内容（只说有没有），与 TMDB 密钥的处理一致。

## 外链：无状态签名 token

`GET /s/<token>/playlist.m3u`（外加同级的 `/s/<token>/<分片>`）给外部播放器用，不需要登录。

token = `<频道id>-<过期unix秒>-<HMAC 前 16 字节>`，用主密钥**派生**出的 HMAC 密钥签名
（`secrets.Cipher.Sign(domain, msg)`，domain 做用途隔离）。校验三件事：格式、签名（常数时间比较）、
过期。签名不对 401、过期 410、频道停用 403。

为什么不落库：token 只表达「哪个频道 + 到什么时候」，服务端能自证真伪，不存表就不用清理、
重启也不丢。M7 要做「限次数 / 限下载」时才需要引入带状态的分享表。

分片用**相对文件名**，客户端以 `/s/<token>/` 为基准去拼 —— 所以分片路由必须与播放列表同级。

## 订阅源刷新与频道探测（S4）

这两件事是同一个包里的（`internal/livetvsync`）：「拿库里的行去拉流/探流，再写回库里」。
实现与解析（`internal/livetv`）、落库（`internal/store`）分开 —— 放到 `livetv` 里会成环
（`store` 反而要 import `livetv` 的 `Entry` 与 `Kind`）。

### 定时刷新：调度器只判断「该不该刷」

- **间隔属于源，不属于调度器**：每个源的 `refresh_interval_minutes`（0 = 不自动刷）。
  调度器每一跳只问一次库：`store.ListTVSourcesDue` 把「开着自动刷、kind=url、
  `last_refresh_at` 比 `now() - interval` 更早」的源挑出来。改间隔**不必重启**。
- 调度器只在 `[livetv] auto_refresh = true`（默认）时启动；关掉只是关掉「自动」那一路，
  界面上的手动刷新与 `lmby livetv refresh` 照旧可用。
- **串行刷**：订阅源是外部服务，同时打几个过去不礼貌；单个源失败只写进它自己的
  `last_status`，不影响其它源（失败也留痕，否则界面上只会看到「上次成功」的时间）。
- 导入是**串行化**的（`importMu`）：手动刷新 / 定时刷新 / 新建源可能撞在一起，
  同一个源被并发导入会在 url 唯一索引上互相打架，最后表现为看不懂的「刷新失败」。

### 探测：真连一次源站

判定「这个频道能不能看」只有真连一次才知道：播放列表里的死源不少照样能建 TCP
连接，是在协议握手（RTSP DESCRIBE）那一步 302 跳到连不上的地址上的。所以：

- 用 **ffprobe 走完整握手**，参数与播放**共用一份**（`livetv.InputArgs`：rtsp 走 tcp + 读超时、
  rtmp 声明 live、自定义请求头透传）。两边各写一套的话，「探得通却播不了」迟早变成常态。
- 判定结果写回 `probe`（人话摘要，形如 `H.264 1920x1080 / MP2 立体声 48kHz（1.1s）`）与
  `probe_ok` / `probe_at`。摘要里带上真实流信息，是因为「通了但是个没音轨的源」也值得看见。
- **先确认 ffprobe 能跑**，跑不了就**一条结果都不写** —— 把「工具没装/路径写错」写成
  「所有频道都失效」是最糟的失败模式（curl 这种预检在验收里能拦住）。
- 可以选范围：`onlyUnknown`（只补没探过的）/ `group`（只探一个分组）/ `channelIds`
  （只探指定几条）。全量探测要真连几百个源站、以分钟计，所以「选范围」是常用路径。
- **进度从库里现算**（`probe_at` 为空 = 未探），只有「在不在跑」是内存态：
  刷新页面、进程重启都不会把进度归零；中断后再点一次「补探」就从剩下的继续。
- 单飞：同一时间只允许一次探测（重复请求 409）。

### 真跑实测（重庆联通单播源 150 台，i5-10500T 容器内）

| 项 | 值 |
|---|---|
| 全量探测 | 4 并发 **164 秒** / 单并发 **642 秒**；判定都是 通 67 / 不通 83（集合一致） |
| 可用的源起播 | 一手真连探测 0.3~0.8 秒返回流信息；播放路径 300~660 ms 拉起（S2 的数据） |
| 摘要样例 | `H.264 1920x1080 / MP2 立体声 48kHz（1.1s）` |

并发填多少只影响耗时，不影响判定（至少在**这台源站**上如此）。如果换一台源站发现
并发越高「不通」越多，那就是源站限并发——把 `probe_concurrency` 调到 1~2 重探一遍即可；
反正探测结果本来就可以随时重探覆盖。

### 命令行

```
lmby livetv status                    # 源清单（含 due 判定）+ 探测总账，JSON
lmby livetv refresh [--all]           # 默认只刷到点的；--all 忽略间隔
lmby livetv probe [--only-unknown] [--group 央视]
```

服务的定时刷新与这三条命令**共用同一套实现**，所以不会出现「命令行刷得动、服务里刷不动」。

## 验收

- `scripts/dev/verify-livetv.sh`：32 项（源、频道、增量导入不冲用户状态、过滤、收藏、导出、权限）。
- `scripts/dev/verify-livetv-play.sh`：30 项（起播耗时、滚动窗口、分片 `no-store`、共享一路、
  停一路不全灭、空闲回收、外链 token 及篡改/伪造/未登录）。
- `scripts/dev/verify-livetv-sync.sh`：**60 项**（刷新与探测）。它**自造源**：
  本机起一个静态 HTTP，摆「一条真视频 + 一条连接被拒 + 一条不应答」三个频道，
  以及在同一个 HTTP 上挂一份订阅列表（验 url 型源的刷新路径），
  最后临时把 `[livetv] refresh_tick_seconds` 调到 5 并重启服务，真验一遍调度器会不会自己刷；
  验完恢复配置。真实 IPTV 源不适合做断言的依据（今天通明天不通）。
- `scripts/dev/livetv-ui-test.mjs`：**42 项**（CDP 驱动真 Chrome，跑在开发机上、连实例）。
  从导航点进直播页，真点按钮（收藏/停用/播放/停止/筛选），并且每次都**回读接口确认真的落库**；
  **浏览器端起播耗时就在这一步量**（点击 → `playing` 事件）；普通用户视角也跑一遍
  （看不到源/探测面板，但能起播）。它跑在开发机上（要本机有 Chrome），环境变量只需要
  `BASE` / `LMBY_USER` / `LMBY_PASS`（可选 `LMBY_USER2` / `LMBY_PASS2` 就是为了验普通用户视角）。
- 真源从 `LIVE_M3U=` 传进来（仓库里只有假地址样例），缺省时用样例并跳过「台数」类断言。
- 改过 `internal/stream` 必须回归：`verify-play.sh`（108 项）与 `verify-transcode.sh`（100 项）。

DoD 实测（一台真实实例 + 真实 IPTV 单播源）：导入 149 台；起播 1351 ms（服务端口径）；
两人同看只跑一路 ffmpeg；无人观看 45 秒退出。**浏览器端起播另测：691 / 1145 / 1475 ms**
（三次运行，均在 DoD 的 2 秒以内）。

## 界面（S3，2026-09-22）

`web/src/pages/LiveTV.tsx`（导航「直播」）+ `components/LiveSources.tsx`（源/探测，仅管理员）。
四个刻意的选择：

- **列表与播放同页**，不是「列表 → 点进播放页」：直播就是不停切台的场景，
  每切一次台都要返回上一页是多一道手；频道行自己会把“正在播”那条标出来。
- **播放器用原生 `<video controls>`**：直播没有进度、没有音轨/字幕选择，
  点播那套自研控制条在这里只是多余；原生控件自带音量、全屏、画中画。
- **切台/关页面就退订阅**（`pagehide` + `sendBeacon`）：不退的话服务端会为一个
  没人在看的频道白跑到空闲回收（最多 45 秒），而 IPTV 源站通常按连接数算钱。
- **筛选全在服务端做**（`q`/`group`/`enabled`/`favorites`/`probe`）：播放列表动辄一两百台，
  放到前端过滤既费流量又容易与“总数/启用数”这些汇总数字对不上。

界面验收 `scripts/dev/livetv-ui-test.mjs` **42/42**，截图 `docs/images/livetv.png`、
`docs/images/livetv-player.png`。

## 已知缺口

- 界面还没有的：频道排序拖拽、批量选择（批量停用/删除）、logo 本地缓存。
  另：**EPG / 录制** 属于二期（M9 候选），频道列表里没有节目单。
- 1 秒分片让请求数翻倍，弱网下表现未测；窗口大小目前是常量（要可配置应加在 `Spec` 上）。
- 探测不支持「取消」：跑起来就得跑完（要么等它结束、要么重启服务）。
  它每探完一条就落库，所以中断也不会留下假状态。
- 直播没有“回看/时移”：滚动窗口只留最近 ~10 秒，往后拖不了（这是 IPTV 单播源的客观限制）。
- Safari / iOS 的直播路径代码就位（原生 HLS），仍**没有真机验证**。
