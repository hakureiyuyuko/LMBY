# 文本编码：不受控文本与 UTF-8 数据库（设计笔记）

> 起因：2026-09-25 验证实例上的扫描记录显示「**状态：失败** / 错误：`写入扫描问题失败:
> ERROR: invalid byte sequence for encoding "UTF8": 0xde 0x20 (SQLSTATE 22021)`」，
> 而同一页下面列着 63 条问题、耗时写着 0.0 秒。

## 一、现象背后的三件事

库是 **UTF-8** 的 PostgreSQL（这是硬前提，建库时 `store.Open` 会检查编码，
不对就拒绝启动 —— 见 `docs/notes/search.md`）。字符串里只要有非法字节，PG 直接
`22021` 拒收。而 LMBY 有两条路会把非法字节喂进去：

1. **文件系统**。SMB / NTFS / 网盘共享上的文件名**不保证是 UTF-8**：客户端用
   `iocharset=utf8` 挂载（我们的验证实例就是 `cifs, iocharset=utf8, mapposix`）时
   是原样透传字节的。实测那个共享上就有一个名字含裸字节 `0xde 0x20` 的文件。
2. **按字节截断**。`s[:n]` 会从多字节字符中间切开。日志里的实证是
   `标记探测失败失败: ... 0xe3 0x80 0xe2` —— `0xe3 0x80` 是被切开的三字节汉字的前两字节，
   紧跟的 `0xe2 0x80 0xa6` 是截断函数补上的省略号「…」。

## 二、为什么「一条坏路径」=「整个扫描失败」

`AddScanIssues` 是**整批**写的（`CopyFrom`，30k 文件的库会有几千条问题，逐条太慢）。
坏路径是这样连锁的：

```
坏名字文件 → InsertFile 失败(22021) → 记一条 issue（它的 path 就是那串坏字节）
          → 整批 CopyFrom 失败 → 逐条兜底又在**这一行**中断并返回错误
          → 扫描被判 failed，其后所有问题丢失（实测库上只留下前面写进去的 63 条）
```

还有两个次生现象，都会让人更看不懂：

- `stats.Issues` / `stats.ElapsedMS` 原本在 `w.finish()` **之后**才赋值，而写问题清单
  就在 `finish()` 里 —— 一失败就提前 return，界面上于是出现「耗时 0.0 秒 / 问题 0」
  却列着 63 条问题的自相矛盾记录；
- 错误里只有一句「写入扫描问题失败」，**没说是哪一条**（这正是排查时最费时间的地方）。

## 三、怎么做（三层，缺一不可）

1. **`internal/textutil`**：`Valid`（非法字节 → U+FFFD）、`Truncate`（rune 安全截断，
   真截了才补「…」，输出保证合法 UTF-8）、`FirstInvalid`（报出坏字节的十六进制，
   取「首字节 + 紧跟的 1 个字节」，与 PG `22021` 报的那两个一致）。
   **全仓不再有手写的 `s[:n]` 截断**：ffprobe stderr、HTTP 响应体、User-Agent、
   直播探测状态、探测失败原因都改走它。
2. **入库边界兜底**：`AddScanIssues`、`MarkFileProbeFailed` 写库前过一遍 `Valid`。
   最坏情况是「那一条的坏字节显示成 U+FFFD」，而不是整批/整个任务失败。
   同时把失败信息带上「第几条 + 路径」，别再让人猜。
3. **扫描器识别并跳过**：遍历时名字不是合法 UTF-8 的条目直接跳过（目录整棵跳过），
   记一条 warning：`文件名含非 UTF-8 字节（0xde 0x20），已跳过：数据库是 UTF-8，
   存不下这个路径；把文件改名后重扫即可`。

第 3 步选了「跳过 + 记问题」而不是「替换成 U+FFFD 后照常入库」：后者存进去的是**假路径**，
探测和播放永远打不开那个文件，比明确告诉用户「这个文件名 LMBY 用不了，改个名」更糟。

## 四、纪律（写代码时照这个来）

- **任何**来自文件系统或外部进程的字符串，进数据库之前过 `textutil.Valid`；
- **任何**「截短」都用 `textutil.Truncate`，不要写 `s[:n]`（`n` 是字节数就是错的方向）；
- 新增会存路径 / 存外部文本的列或写库函数时，想一下「这串东西有没有可能是非法 UTF-8」；
- 界面上出现 U+FFFD 是**有意**的：它说明这里原本有个存不下的字符，比静默丢掉诚实。

## 五、验收

`scripts/dev/verify-scan-badname.sh`（真库 + 真文件系统）：造一个正常文件、一个坏名字文件、
一个坏名字目录（内含正常文件），扫一次，断言：

- 扫描 `state=done`（**旧代码在这里是 failed**，这是回归点）；
- 坏名字各记一条问题、带十六进制、路径用 U+FFFD 标出坏字节；
- `stats.issues` / `stats.elapsedMs` 有真实值；
- 正常文件入库；坏命名目录里的文件**不**入库。

实例测量值（不是项目常量）：旧构建 `dev-bf15b2a` 跑同一脚本 `7 过 / 7 败`
（`state=failed`、`issues=0`、`elapsedMs=0`），修后 `14 / 14`。
