# 扫描与网络盘挂载（设计笔记）

> 背景：媒体库常常挂在 SMB / NFS / 网盘上，**这些挂载会掉线**。掉线时扫描「看不见文件」，
> 而这和「文件真的没了」在代码里长得一模一样 —— 这份笔记记的就是怎么把两者分开。

## 一、踩过的事故（2026-09-25，验证实例）

| 时刻 | 发生了什么 |
|---|---|
| 09-25 09:57 定时扫描 | CIFS 掉线：每个库根只产出一条 `访问失败: lstat /mnt/media/…: host is down`，`videos=0`，然后走删除步骤 → `deletedFiles=38437`（**整库软删**），扫描状态还是 `done` |
| 之后每次重扫 | 文件在磁盘上都在，但都被扫成「消失」了；增量状态只读**活着的行** → 它们被当新文件去插 → 撞 `media_files.path` 唯一约束 → 每条都报「该路径已被其它条目占用，已跳过」→ **文件永远回不来**（库里 38461 个文件被这么钉死） |
| 顺带 | 每轮重扫还在造新条目（`ensureItem` 跑在插文件之前）：40 剧集 / 69 季 / 888 集，其中约 876 集一个文件都没挂 |

教训：**软删除不是安全阀**。软删除只解决「硬删会丢数据」，但光有它，一次掉线依然能让整个库
从界面上消失，而且**自愈不了**。

## 二、三道护栏（都在 `internal/scanner`）

### 1. 读不到的子树，一律不参与删除判定（硬规则）

`filepath.WalkDir` 会在读不到的位置上报错（根掉线、子目录掉权限）。扫描器把这些位置记下来
（`noteUnreadable`），删除判定时跳过它们下面的文件（`underUnreadable`，按**路径前缀**比较，
用 `strings.HasPrefix(p + separator)` 以免把 `…/连载动画2` 也当成 `…/连载动画`）。

- 全部根都读不到 → 本次扫描**判失败**，并在 error 里写清「本次没有删除任何文件」。
  报成功会比删文件更糟：用户会以为库真的空了。
- 只有部分根 / 某个子目录读不到 → 扫描可以成功，但会记一条 warning，并把这些文件计入
  `skippedDeletions`。

### 2. 比例闸：一次扫描不许删掉太多（`[scan] max_delete_ratio`）

有些掉线形态**不报错**（挂载点还在、目录读成空的），护栏 1 拦不住。所以再加一道：
要删的文件占存活文件的比例超过阈值（默认 **0.2**）时，**一个都不删**并判失败。

- 有最小规模 `minFilesForDeleteGuard = 20`：小库删两个就少一半，按比例卡会把正常运维也拦下来。
- 配置语义：`0` = 内置默认、负数 = 不限制（真要删掉大部分文件时的出路）、正数 = 自定义。
- **墓碑行（已软删的行）不计入分母**：算进去会把比例冲淡、安全阀形同虚设。

### 3. 同一路径回来 → 复活，而不是当新文件插

`ListLibraryFiles` 现在把**墓碑行也读出来**（`LibraryFile.DeletedAt`），扫描器在
「路径已存在」这条快速路径上发现 `DeletedAt != nil` 就调 `ReviveFile`：清 `deleted_at`、
更新 size/mtime，指纹变了就把 `probe_state` 退回 `pending`（内容变了要重读流信息）。

为什么必须复活而不能插入：`media_files.path` 上是**全量唯一索引**，墓碑行照样占着那个路径。
插入只会拿到 `ErrAlreadyExists`，然后记一条「该路径已被其它条目占用」的**假警告** ——
既没恢复数据，又把界面刷满噪声。

顺带：这条路也顺手堵住了上面那条「重扫造重复条目」的损伤 —— 已知路径不再走 `ensureItem`。

## 三、验收

`scripts/dev/verify-scan-robust.sh`（真库 + 真文件系统，24 个文件越过安全阀规模，另加一个小库）：

| 场景 | 期望 |
|---|---|
| 库根整个不见（挂载掉线） | 扫描 `failed`、`deletedFiles=0`、`unreadableRoots=1`、问题里有「访问失败」 |
| 根回来 | 一切照旧（24 个文件未变、没删） |
| 目录还在但读成空的 | `failed`、`deletedFiles=0`、`skippedDeletions=24`、error 提到 `max_delete_ratio` |
| 24 个文件放回（没被删过） | 不是「新文件」（`newFiles=0`）、不删、无「已被其它条目占用」 |
| 单个文件删掉再放回 | `revivedFiles=1`、无假警告 |
| 小库（4 个文件）删光再放回 | 先软删 4 个（小库不设闸）、再全量复活 4 个 |

实例测量值（不是项目常量）：同一脚本在旧构建 `dev-0ad7364` 上 **19 过 / 15 败**
（`state=done` 却删了 24 个；放回后全是「已被其它条目占用」），修后 **34 / 34**。

## 四、同一部被造出好几份（已修，单独成文）

掉盘那次的连带损伤里最脏的一块：整库软删后每轮重扫都把几万个文件当「新文件」，
于是「按标题+年份找条目」这一步反复查不到自己，一次造出几十个重复剧集 +
几百个空壳集（就是界面上「集没标题、点了放不了」的那种）。

根因与修法（条目身份 `scan_key`）见 **`docs/notes/scan-identity.md`**：
身份不再用会被 nfo / 刮削改写的标题与年份，而是扫描器建档时写下的稳定键。
验收脚本：`scripts/dev/verify-scan-identity.sh`。
