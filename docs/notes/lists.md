# 列表（收藏 / 播放列表 / 合集）设计笔记

> 取舍与真跑实测。标「实测」的数字都是在一台真实实例上量出来的，不是项目常量。

这一篇按实现的先后分节写：**收藏**（第一段）→ 播放列表 / 合集（第二段）。

## 一、收藏：为什么是独立一张表、独立一组接口

### 表：`favorites (user_id, item_id, created_at)`，主键 `(user_id, item_id)`

- **归属按账号**：M7 的多用户要的就是这个语义 —— 妈妈收藏的动画片不该出现在孩子的列表里。
  写在 `media_items` 上的布尔列或 jsonb 数组是「单人版」的写法，多用户一上来就得推倒重来。
- **主键 `(user_id, item_id)`** 让「收藏两次」变成 `on conflict do nothing` 的幂等操作 ——
  界面上的爱心按钮会被连点、会被重试，接口必须吃掉重复。
- **「收藏数」不另存计数器**：全站视角的那个数用 `count(*) from favorites where item_id = $1`
  回答（`favorites_item_idx` 撑着）。收藏是低频写、高频读，加计数器只会多一处会漂移的状态。

### 接口：三个，而不是往条目接口里塞

| 接口 | 干什么 |
|---|---|
| `GET /api/v1/favorites?kind=&limit=&offset=` | 我的收藏（可过滤、可翻页） |
| `GET /api/v1/items/{id}/favorite` | 单条状态：我收藏了没 + **全站**收藏数 |
| `POST /api/v1/items/{id}/favorite` | 收藏 / 取消（幂等，响应回新状态与新总数） |

**为什么不把「我收藏了没」放进 `GET /api/v1/items/{id}`**：那个接口是编辑页在用的，
不该因为界面多了一个爱心按钮就多查一张表；更要紧的是收藏状态**随账号而变**，
混进条目本体以后同一份 JSON 对不同账号含义不同 —— 将来做缓存会很难受。

`POST` 的响应里直接回**新状态与新总数**，界面拿到就更新按钮与计数（少一次往返，
也少一次「按钮和数字不同步」的机会）。

### 验收里的多用户隔离

`scripts/dev/verify-favorites.sh` 会**造一个临时账号**（`lmby user add`）来验隔离：
他看不到我的收藏、他的收藏列表是空的、他收藏之后我的列表条数不变，
而「全站收藏数」确实变成 2。跑完用 psql 删掉临时账号（级联带走它的收藏行）。

> 这是本项目第一条**真的验到多用户**的脚本。M7 之前，用户相关的功能都得这么验一遍。

## 二、播放列表 / 合集：一张表、两种 kind

### 表：`playlists` + `playlist_items`

两者**结构完全一样**（一串有序条目 + 名字 + 说明），差别只在可见性与谁能改，
所以共用一张表、靠 `kind` 区分：

| kind | 可见性 | 谁能改 |
|---|---|---|
| `playlist` | 只有主人 | 只有主人 |
| `collection` | **所有人** | 任何管理员 |

做成两张表的代价是「加入列表」的接口要复制一份、有序条目的排序逻辑要复制一份，
而唯一差别只是 `where` 上的一个条件。

几个具体决定：

- **有序条目用 `sort_order` 整数字**，重排是「整串按新顺序写一遍」（一次事务、一次写入、
  没有中间态）。链表要改两行、浮点会慢慢退化，而列表也就几十上百条，
  整串重写的代价可以忽略。
- **同名不重**：`unique (user_id, kind, lower(name))` —— 同一个人的列表名不重（不分大小写），
  合集之间也不重；重名回 409 而不是 500。
- **删除列表不动媒体文件**：删的只是 `playlists` 一行，`playlist_items` 随级联走。
  确认文案里明确写了这句（用户很怕「删列表＝删片」）。
- **「加入」是幂等的**：`on conflict (playlist_id, item_id) do nothing`，
  响应里的 `added` 能区分「刚加进去」与「本来就在里面」，界面据此给不同文案。
  加入时用 `array_position` 保住调用方给的顺序（否则 Postgres 的返回顺序不可指望），
  并用 `deleted_at is null` 顺手挡掉扫不见的条目。

### 权限：只在 store 里判一次

API 层不自己做判断，只把身份原样传下去（`store.Viewer{UserID, IsAdmin}`），
**判定只写在 `store/lists.go` 的三个方法里**（`canSee` / `canEdit` + SQL 里的同一个条件）：

- 看不见的列表 → **404**（而不是 403）—— 不区分「不存在」与「不给你看」，
  免得用状态码差异就能探出别人有哪些私人列表；
- 看得见但不能改 → **403**（合集本来就公开，不存在泄露）；
- 「用户输入不合法」用 `store.InvalidInputError` 单独一类，API 映射成 **400**——
  否则日志里全是假 5xx，真正要看的报错被淹没。

### 播放器里的「下一项」

列表详情页的「播放全部」跳 `/play/{第一条}?list={id}`，播放器拿 `?list=` 去问
`GET /api/v1/playlists/{id}/neighbors?itemId=`，只取三个数（`prevId` / `nextId` / `index`）：
列表可能有几百条，而这一步**每次切集都要跑**，传整个列表划不来。

邻居用 `(sort_order, added_at)` 的**行值比较**：`sort_order` 可能并列（历史数据或刻意并列），
只比 `sort_order` 会漏条或跳条。

## 四、这一轮踩的坑

1. **`select <一长串列> ... join <带 id 的 CTE>` → `column reference "id" is ambiguous`**
   （500；首页那次踩过，这里又差点）：CTE 里的列改名成 `item_id` 就好。
2. **界面验收里「点得太早」会假通过**：刚 `Page.navigate` 过去时 DOM 还是空的，
   `点击`找不到元素（静默返回 false），而紧接着的「卡片消失了吗」查询也是空 DOM → 真空通过。
   凡「点了会消失 / 会删除」的断言，必须先等目标元素真的渲染出来。
3. **删除类操作的确认框在无头浏览器里不能用真点击**：`window.confirm` 拿不到用户输入。
   验的是「确认之后到底删不删」，所以直接替掉 `confirm`，分两次（先 `false` 验「取消不删」、
   再 `true` 验真删）。
4. **轮询后端状态要加缓存扰动**：没有缓存头的 JSON 响应，浏览器会做启发式缓存 ——
   同一 URL 连着翻几个轮子可能一直拿到同一份旧响应。验收里的 `GET` 都带一个 `_=时间戳`。
5. **只差一个字段的 PATCH 得用指针**：`name`/`overview` 如果都用空串表示「不改」，
   界面只改名字就会把说明抹掉；用 `nil` 表示不改、空串表示清空，两者才区分得开。
