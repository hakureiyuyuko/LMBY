# 列表（收藏 / 播放列表 / 合集）设计笔记

> 取舍与真跑实测。标「实测」的数字都是在一台真实实例上量出来的，不是项目常量。

这一篇按实现的先后分节写：**收藏**（第一段）→ 播放列表 / 合集（第二段）。

## 一、收藏：为什么是独立一张表、独立一组接口

### 表：`favorites (user_id, item_id, created_at)`，主键 `(user_id, item_id)`

- **归属按账号**：M7 的多用户要的就是这个语义 —— 妈妈收藏的动画片不该出现在孩子的列表里。
  写在 `media_items` 上的布尔列或 jsonb 数组是「单人版」的写法，多用户一上来就得推倒重来。
- **主键 `(user_id, item_id)`** 让「收藏两次」变成 `on conflict do nothing` 的幂等操作 ——
  界面上的爱心按钮会被连点、会被重试，接口必须吃掉重复。
- **「收藏数」不另存计数器**：全站视角的那个数用 `count(*) from favorites where item_id = $1`
  回答（`favorites_item_idx` 撑着）。收藏是低频写、高频读，加计数器只会多一处会漂移的状态。

### 接口：三个，而不是往条目接口里塞

| 接口 | 干什么 |
|---|---|
| `GET /api/v1/favorites?kind=&limit=&offset=` | 我的收藏（可过滤、可翻页） |
| `GET /api/v1/items/{id}/favorite` | 单条状态：我收藏了没 + **全站**收藏数 |
| `POST /api/v1/items/{id}/favorite` | 收藏 / 取消（幂等，响应回新状态与新总数） |

**为什么不把「我收藏了没」放进 `GET /api/v1/items/{id}`**：那个接口是编辑页在用的，
不该因为界面多了一个爱心按钮就多查一张表；更要紧的是收藏状态**随账号而变**，
混进条目本体以后同一份 JSON 对不同账号含义不同 —— 将来做缓存会很难受。

`POST` 的响应里直接回**新状态与新总数**，界面拿到就更新按钮与计数（少一次往返，
也少一次「按钮和数字不同步」的机会）。

### 验收里的多用户隔离

`scripts/dev/verify-favorites.sh` 会**造一个临时账号**（`lmby user add`）来验隔离：
他看不到我的收藏、他的收藏列表是空的、他收藏之后我的列表条数不变，
而「全站收藏数」确实变成 2。跑完用 psql 删掉临时账号（级联带走它的收藏行）。

> 这是本项目第一条**真的验到多用户**的脚本。M7 之前，用户相关的功能都得这么验一遍。

## 三、真跑验收

| 脚本 | 结果 |
|---|---|
| `scripts/dev/verify-favorites.sh` | **30 项断言全绿**（真库、真 HTTP、含临时账号的隔离验证） |
| `scripts/dev/favorites-ui-test.mjs` | **18 项断言全绿**（CDP + 真 Chrome） |

界面这条链是闭环的：详情页点收藏 → 按钮与「N 人收藏」变了、接口也变了 →
首页出现「我的收藏」行且第一条是它 → 再取消收藏 → 两个地方都回到原样。
脚本先记下起点（这个账号本来有没有收藏），跑完还原，所以它不假设库里的状态。
