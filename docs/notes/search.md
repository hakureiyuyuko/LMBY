# 搜索（M2 起，M6 补齐联想与分面）设计笔记

> 这篇记的是**取舍与真跑实测**，不是教程。凡标「实测」的数字都是在一台真实实例上量出来的，
> 不是项目常量（换库、换机器都会变）。

## 一、为什么分成四个接口

| 接口 | 干什么 | 翻页时要不要重算 |
|---|---|---|
| `GET /api/v1/search` | 结果列表（条目），分页 | 要 |
| `GET /api/v1/search/facets` | 结果分面：类型 / 媒体库 / 流派 / **人** 的命中数 | **不要** |
| `GET /api/v1/search/people` | 「人」这一档的结果列表，分页 | 要 |
| `GET /api/v1/search/suggest` | 即时联想（每组几条，只为下拉） | 不翻页 |

分面单独一个接口，理由有两个：

1. 分面只在「查询词或筛选变了」时需要重算，翻页时重算是白算（4 个额外查询）；
2. 分面的统计规则（**每一维统计时都要把自己那一维的筛选关掉**）与结果列表不是一回事，
   塞进同一个响应里会让两边互相牵制、也说不清 `total` 到底是哪一组的。

四个接口用**同一段 SQL 条件串**（`internal/store/search.go` 的 `searchCondition`），
参数位置固定：`$1` 库 · `$2` 类型 · `$3` 流派 · `$4` 人 · `$5` 词。
分面要「关掉某一维」时只需把对应参数换成空值 —— 位置一变条件串就得跟着重拼，容易出错。

## 二、条目与人用同一套三路匹配

`migrations/0007_search.sql` 给标题做了中文二元组切词，M6 的 `0011_search_people.sql`
把**同一个纯函数** `lmby_bigram` 用在人名上（`people.search_vec` 生成列 + GIN + trigram 索引）。
于是「搜标题」与「搜人」的行为完全一致，界面也不需要为两者写两套说明：

1. `search_vec @@ plainto_tsquery('simple', lmby_bigram($q))` —— 分词命中（中文二元组、英文整词），
   要求**全部单元命中**，准，但错字会让整条查不到；
2. `ILIKE '%词%'` —— **子串兜底**：单字（「钢」）在 bigram 索引里查不到（索引里只有两字单元），
   而用户敲下第一个字就期待有反应；
3. `$q <% name` 词相似（pg_trgm）—— **错字容忍**，阈值按会话调到 `0.4`
   （默认 0.6 对中文太严：8 个字里错 1 个，相似度只有 ~0.42）。

⚠️ 第 3 路是**字符类**三元组：只有数据库的 `lc_ctype` 认识中文（如 `C.UTF-8`）才切得出中文三元组，
`lc_ctype=C` 的库里 `show_trgm('中文')` 是空的，这一路会**静默失效**（见 `store.go` 的 `checkEncoding`）。

## 三、分面的一致性原则（本文档最该记住的一节）

规则：**统计某一维的分面时，把这一维自己的筛选摘掉。**

为什么：用户正在看「类型=电影」的结果，如果类型分面是按「全条件」数出来的，那么
「剧集」那一格永远是 0 —— 用户永远切不过去。

由此得到几条可以用来自检的**不变量**（验收脚本按它们断言）：

| 不变量 | 说明 |
|---|---|
| `sum(kind) == total` | 每个条目恰好一个类型 |
| `sum(library) == total` | 每个条目恰好属于一个库 |
| **`sum(genre)` 可以小于 `total`** | 没有流派的作品**不贡献格子**（`jsonb_array_elements_text('[]')` 无行）；条目可以有多个流派，所以和也可能大于 total |
| 关掉某一维后，那一维的分面 == 同一查询去掉该筛选的**全集** | 这才是「关掉自己那一维」的正确表述 |
| 分面数字 == 按那个值真搜到的条数 | **最有价值的一条**：数字不是装饰，点下去必须真能得到那么多 |

其它取舍：

- 流派分面只取前 20 个（几百条命中里的长尾流派对「筛一下」没有帮助）；
- 媒体库分面的 `value` 是**库 id**（字符串），名字由前端用库列表贴上去 ——
  界面本来就为了筛选项拉了库列表，没必要在这里再查一遍；
- 人这一档的命中数只由**查询词**决定：人不是条目，没有库与流派归属。

## 四、「人」这一档

- 数据来自 `people` / `item_people`（迁移 `0010`，nfo 里的 `<actor>` / `<director>` / `<credits>`，
  **不联网、不占 TMDB 配额**）；M6 把这张表接进搜索。
- `works`（作品数）用 `count(distinct coalesce(i.series_id, i.id))`：**集数折进所属剧集** ——
  否则一部 20 集的剧会把一个人算成 20 部作品。
- 点一个人名 → `?personId=N` 并且**清掉查询词**：不然标题也得匹配这个人名，必然 0 条。
  接口层因此允许「查询词为空」，条件是**至少给了一个筛选维度**（库 / 类型 / 流派 / 人），
  否则就是列表接口的活，回 400 —— 不给一个会被误当成搜索结果的响应。

## 五、即时联想（下拉）

- **防抖 200ms**：每敲一个字就发请求会把后端与网络压满，而人的打字间隔通常在 100~300ms；
- **旧响应按自增序号丢弃**：否则「钢」的响应可能晚于「钢炼」到达，把下拉刷回旧的一批；
- **不看当前筛选**：用户还在敲字时用库/流派去套只会让下拉越来越空，筛选是敲完回车之后的事
  （接口也不收这些参数）；
- **与结果同一排序**（复用 `searchOrder`）：不然会出现「回车之后东西换了个位置」；
- **字段是轻量的**：只取 id / title / kind / year（人另给 roles / works），
  不把 29 列与 `overview` 拉回来；
- 只有「用户真敲过」（`touched`）**且**「输入框真拿着焦点」时才自动弹：
  - 从 URL（收藏、后退、别人贴的链接）进来时 value 是被塞进来的，那不是「用户正在找东西」，
    一进页面就弹个下拉很吵；
  - 点「搜索」按钮会让输入框失焦，而那一批联想的响应可能才刚回来 ——
    不判焦点的话下拉会在结果出来之后自己弹回来、盖住刚看到的列表。
  - 焦点直接用 **DOM 的 `document.activeElement`** 判，而不是自己记 focus/blur 事件：
    元素本来就拿着焦点时再调 `focus()` **不会再触发 focus 事件**，
    靠事件维护的状态会跟实际不一致（无头浏览器里真踩到）。

## 七、这一轮踩到的坑（都补进了脚本注释）

1. **分面断言先想清楚「这个数是在哪个集合上数的」**。第一版验收脚本写成
   `sum(kind) == total` 且在「类型=电影」生效时也断言相等 —— 必然失败，因为分面故意
   统计的是超集。**错的断言会把正确实现判成 bug**，比没有断言更浪费（它让人去改对的东西）。
   同理 `sum(genre) >= total` 也是错的（空流派不贡献格子）。
2. **界面验收脚本会悄悄烂掉**：`search-ui-test.mjs` 从 M2 之后再没跑过，
   M6 把卡片改指详情页（`/items/{id}` → `/item/{id}`）、把库/类型下拉换成分面胶囊之后，
   它有 5 条断言**永久失败**。原因是「验收基线表」里没有它，就没人发现。
   改动入口时顺手跑一遍界面脚本，基线表里要留着它。
3. **「把同一个值写回输入框」不会触发联想**：React 状态没变化 → `useEffect` 不重跑 →
   根本不发请求，测试会把好功能判成坏功能。测试要先清空再敲。
4. **JS 的 `.click()` 不触发 `mousedown`**，而下拉是靠 mousedown 收起的 ——
   截图里下拉把半个页面盖住了（真鼠标不会碰到这个差别）。截图前按 Esc。
5. **路由切换后内容不是同一拍就绪的**：点导航进搜索页后立刻查 `.search-input` 会拿到
   `false`（URL 早就变了，DOM 还没渲染完）——界面脚本里凡是「切页之后马上断言」的地方，
   都要先 `waitFor` 目标元素出现。
