# 首页（Netflix 风格）设计笔记

> 这篇记的是**取舍与真跑实测**，不是教程。凡标「实测」的数字都是在一台真实实例上量出来的，
> 不是项目常量（换库、换账号都会变）。

## 一句话

首页只有一个接口 `GET /api/v1/home`，一次给全三段：**大屏轮播（10 条）+ 继续观看 + 推荐行**。

## 一、为什么整页一个接口

- 首页是「一进站就看到」的页面，**首屏感觉直接由请求数决定**；
- 几行之间有**先后关系**：有没有观看记录，决定了出「为你推荐」还是「评分最高」——
  拆开就得让前端去判断只有后端才知道的事；
- 几行共用同一个「现在」，不会出现两行里同一条目的状态不一致。

代价是一次响应偏大（每行 20 条条目的元数据）。真要优化时应该**先压字段**
（列表只需要海报、标题、年份那一小撮），而不是把接口拆散。

## 二、「最新更新/入库」用的是 `updated_at`

轮播与「最近添加」行都是 `order by updated_at desc`：

- 刚扫进来的条目 `updated_at` 就是入库时间；
- 元数据被刮削或人工编辑过也会顶上来 —— 这正是「最新更新」的语义。

只看 `created_at` 的话，**重扫一遍老库什么都不会变**（条目没新增），
「最新更新」就永远停在第一次扫描的那批。

两处是**同一段查询**（只是 limit 不同），所以验收里可以断言
「recent 行的前 10 条与 hero 逐条一致」。

## 三、推荐：离线可算的「流派画像」

不做协同过滤、不联网、不依赖 TMDB（与 `ListRelatedItems` 同一个理由：全本地 nfo 库也要有推荐）。

| 项 | 规则 |
|---|---|
| 画像 | 看过的作品 → 流派 → 权重 = 该流派出现了几次（最多用最近 **50** 条观看记录） |
| 打分 | `score = Σ（命中流派在画像里的权重）`，即「你看得越多的类型越容易再推给你」 |
| 排除 | 粒度是**作品**（`coalesce(series_id, id)`，集折进剧集）：正在追的剧、看完的电影都不再推 |
| 平手 | 评分 → 年份 → id，保证**两次请求顺序一致**（验收有断言） |
| 没有历史 | 退成「评分最高」行 —— 新装实例的首页不该是一行空白，也不该出现「为你推荐（暂无数据）」 |

**把画像本身返回给界面**（`sections[].taste`）是这一块的关键决定：

- 界面用得上：副标题写「因为你看过《X》」（只有一部时）或
  「因为你喜欢 动画 · 剧情（最近看过 6 部作品）」，行头显示画像 chips；
- 验收用得上：脚本能断言「**推荐的每一条都命中画像里的流派**」、
  「刚标记为已看的作品的流派确实进了画像」—— 这是**精确判定**，而不是
  「看起来像推荐」。推荐不能是黑盒，而「可解释」与「可验收」恰好是同一份数据。

## 四、前端取舍

- **轮播 8 秒一张，鼠标悬停即暂停**：自动轮播是「展示」，用户动手时就不该再抢节奏；
  另外给了 ‹ › 与圆点，键盘/触屏用户不必等。
- **宽幅背景 404 → 退海报 → 再退「隐掉图片留渐变」**：任何库都不会出现破图。
  验收里有一条「轮播背景图真的加载出来了」—— 第一次截图横幅是纯黑，
  看着像功能坏了，其实是 1600 宽的图还在路上（见下面的坑）。
- **行复用海报墙的卡片类名**（`.poster-card` / `.poster-frame` / `.poster-body`）：
  卡片长什么样全站只有一套定义，改一处到处都对。
- 首页用更宽的容器（`.content-wide`，1440px）：默认 960px 下横幅显得局促。
- M0 就在首页的**服务状态面板没删**，收成 `<details>` 放到页面底部 ——
  它是实例自检的入口，而 `browser-test.mjs` 还在断言它的文案。

## 五、真跑验收

| 脚本 | 结果 |
|---|---|
| `scripts/dev/verify-home.sh` | **26 项断言全绿**（真库、真 HTTP） |
| `scripts/dev/home-ui-test.mjs` | **34 项断言全绿**（CDP + 真 Chrome） |
| 截图 | `docs/images/home.png`、`docs/images/home-light.png` |

- 后端 26 项：三段形状与上限（hero ≤ 10、每行 ≤ 20）、hero 都是顶层条目且按 `updated_at` 倒序、
  recent 与 hero 逐条一致、**自造一条观看记录后**的推荐正确性（不含刚看过的、
  每条都命中画像、画像里确实多了它的流派、副标题说得清依据、两次请求顺序一致）、跑完还原、401。
- 界面 34 项：圆点数量与接口一致、点圆点/箭头切换、**自动轮播（等 9 秒真验）**、
  背景图加载、每行卡片数与接口一致、行右滚（`scrollLeft` 真的变了）、
  推荐依据（副标题 + 画像 chips）、点卡片进详情页、服务状态折叠面板仍在、亮暗主题。

## 六、这一轮的坑

1. **`select <一长串列> ... join <带 id 的 CTE>` → `column reference "id" is ambiguous`（500）**。
   把 CTE 的列改名成 `item_id` 就好了。记一笔：这种「列名撞车」在拼 SQL 时很容易发生，
   报错还算好的（更坏的是不报错但算错）。
2. **Go 的原始字符串（反引号）里不能出现反引号**：我在 SQL 注释里写了 `` `select id, …` ``，
   于是字符串提前结束，`go build` 报 `unexpected keyword select`。
   SQL 注释里别用反引号（用「」）。
3. **截图要等图片真的加载完**：第一次首页截图的横幅是黑的 —— 图还在路上。
   验收脚本里先等 `img.complete && naturalWidth > 0` 再截图，
   顺带把「图挂了」也变成一条真断言（本来只是看着不对）。
